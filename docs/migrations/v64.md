# v64 — Row provenance columns on `soldiers` (issue #377)

The v64 schema migration adds two row-level metadata columns to the
`soldiers` table so every Person Record / Event Record / Article
Record carries the DixieData release + the code path that wrote it.
The motivating case is the #376 diagnostic trail for soldier id=411:
30 minutes of git-archaeology + timestamp cross-referencing would
have collapsed into one query with these columns.

## Headline changes

- **Two new columns on `soldiers`**:
  - `created_by_version TEXT NOT NULL DEFAULT ''` — DixieData
    release string, e.g. `"v1.2.64"` (the v-prefix matches the
    `v1.2.{N}` tag convention per Decision 5).
  - `created_by_import_path TEXT NOT NULL DEFAULT ''` — stable
    snake_case string, e.g. `"create_soldier"`,
    `"memorial_json_import"`, `"restore_backup_archive"`,
    `"cli_export"` (per Decision 4).
- **Backfill** rewrites every row with `''` in either column to
  `"unknown"`. The DEFAULT `''` on fresh installs means the
  backfill is a no-op there (inline schema carries the column); on
  v62→v63→v64 archives that upgraded without populating the column,
  every row lands with `''` and the backfill fills `"unknown"`.
- **Read paths** gain the two columns at the end of
  `soldierSelectColumns` (soldier_service.go:23) + matching
  `soldierScanDest` entries. Backward compat: existing callers
  that don't populate `models.Soldier.CreatedByVersion` or
  `models.Soldier.CreatedByImportPath` continue to work unchanged
  (the struct fields default to `""`; the INSERT writes `""`; the
  backfill rewrites them to `"unknown"` on the next migration run).

## Update semantics (Decision 3, locked)

The existing `UPDATE soldiers SET ...` statement in
`soldier_service.go:372` does NOT list `created_by_version` or
`created_by_import_path`. The columns are **frozen at the moment
the row entered the table** and never rewritten by Update.
Proven by `TestSoldierService_UpdateFreezesCreatedProvenance`.

## Fresh-install vs upgrade path

- **Fresh installs** ship with both columns in the inline `const
  schema` `CREATE TABLE` statement. The v64 ADD COLUMN statements
  guard themselves via `columnExists` (no-op when the new column
  is inline). Backfill rewrites `''` → `'unknown'`; on fresh
  installs every row has `created_by_* = ''` (the DEFAULT), so
  the backfill assigns `'unknown'` to every row. Future Create
  callers stamp the columns (Slice 2) and the backfill is a one-
  time stamp-on-upgrade migration.
- **v62 / v63 → v64 upgrades** run the v64 block once. Block 64's
  sub-block A adds `created_by_version` + backfills `'unknown'`;
  sub-block B adds `created_by_import_path` + backfills `'unknown'`.

## Backfill best-effort (Decision 6, locked)

The v64 backfill does NOT try to guess the DixieData version that
wrote a pre-v64 row (no git-archaeology pass; the issue body
mentioned it as a possible enhancement but locked as best-effort).
Every pre-v64 row lands with `created_by_version = 'unknown'` and
`created_by_import_path = 'unknown'`. The future Slice 2 handler
stamping populates these columns on every Create going forward; the
diagnostic power of the column comes from post-v64 rows. A future
migration (not in scope for Slice 1) could implement the
git-archaeology heuristic if the diagnostic trail ever surfaces
again.

## Reversibility

The v64 block is **Reversible** per `docs/migrations/reversibility.md`.

- `ADD COLUMN` is reversible (`DROP COLUMN` works because both
  columns are not FK-constrained and have no inbound references).
- The backfill `UPDATE` is reversible (no-op reverse on DOWN — rows
  lose their `'unknown'` values; the read path stops returning
  them).
- No data loss on DOWN (the values are metadata, not domain data).

## Existing archives migrate transparently

Both columns default to `''` on ADD COLUMN; the backfill rewrites
every row's `created_by_*` to `'unknown'`. No manual steps.

Bumps `CurrentSchemaVersion` to 64.

Rollback: `bump-version.ps1` without `-Force` refuses any downgrade
that would drop a column required by live code; v64 → v63 succeeds
because the columns have no inbound FK + no domain-data dependency.
