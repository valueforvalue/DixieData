# v63 — `sort_order` columns on `records` + `event_sources` (issue #368)

The v63 schema migration adds a user-controlled ordering column to the
two Source Record tables so researchers can reorder their attached
evidence after the fact. Today both lists display in `id` (insertion)
order; with `sort_order` the read paths sort by it and a PATCH endpoint
can move a source to a new position in one transaction.

## Headline changes

- **New `sort_order INTEGER NOT NULL DEFAULT 0`** column on both:
  - `records` (`internal/db/schema.go:85`)
  - `event_sources` (`internal/db/schema.go:322`)
- **Read paths change `ORDER BY id` → `ORDER BY sort_order, id`**
  (the secondary `id` keeps the order stable when two rows tie on
  `sort_order`). Three call sites:
  - `internal/records/soldier_service.go:251`
  - `internal/records/soldier_service.go:299`
  - `internal/records/event_service.go:75`
- **Write paths** are NOT touched by this slice — Slice 2 of #368
  updates `replaceRecords` + `EventService.AttachSourcesToEvent` to
  set `sort_order` from the form-array index, and Slice 3 adds the
  PATCH `/soldiers/{id}/sources/{sourceId}/position` and
  `PATCH /events/{id}/sources/{sourceId}/position` endpoints. Slice 1
  is the tracer bullet: schema + read path only, so the existing
  insert paths continue to write `sort_order = 0` (the default) and
  the backfill preserves the previous `id` order on first read after
  upgrade.

## Backfill

A single `UPDATE` per table assigns `sort_order = id` for existing
rows. Both `id` (auto-increment, insertion-order) and the backfill
target are `INTEGER`, so the assignment is type-safe with no
cast. The result: every existing row gets a unique `sort_order`
matching its current display position; ties are impossible because
`id` is unique within each table.

```sql
-- records
UPDATE records SET sort_order = id WHERE sort_order = 0 OR sort_order IS NULL;

-- event_sources
UPDATE event_sources SET sort_order = id WHERE sort_order = 0 OR sort_order IS NULL;
```

The `OR sort_order IS NULL` guard handles archives upgraded via the
ADD COLUMN path on older archives where the column was added without
DEFAULT 0 (none exist today, but the guard is free). On fresh installs
the inline `CREATE TABLE` carries `sort_order INTEGER NOT NULL DEFAULT
0` so the backfill is a no-op (every row already has `sort_order = 0`,
and `UPDATE ... WHERE sort_order = 0` would set them all to `id` —
still correct, just one extra write per row).

## Fresh-install vs upgrade path

- **Fresh installs** ship with `sort_order INTEGER NOT NULL DEFAULT 0`
  in the inline `const schema` `CREATE TABLE` statements for both
  `records` and `event_sources`. The v63 ADD COLUMN statements guard
  themselves via `columnExists` (no-op when the new column is inline).
- **v62 → v63 upgrades** run the v63 block once. Block 63's
  sub-block A adds `sort_order` to `records` (with backfill);
  sub-block B adds `sort_order` to `event_sources` (with backfill).
  The three read paths flip to `ORDER BY sort_order, id` on the
  next read.

## Reversibility

The v63 block is **Reversible** per `docs/migrations/reversibility.md`.

- `ADD COLUMN` is reversible (`DROP COLUMN` works because `sort_order`
  is not FK-constrained and has no `NOT NULL` constraint other than
  the DEFAULT 0 fallback).
- The backfill `UPDATE` is reversible (no-op reverse — values revert
  to `0` on DROP, the read path flips back to `ORDER BY id` via the
  v62 code).
- The read-path `ORDER BY` change is code, not schema — reverts on
  code revert.

The DOWN runner handles v63 → v62 (per the
`TestApplyDownSchema_ReversibleStepDown` family); the inline schema
revert for fresh installs is a code revert, not a schema revert.

## Existing archives migrate transparently

Both `sort_order` columns default to `0` on ADD COLUMN; the backfill
rewrites every row's `sort_order` to its `id`. No manual steps.

Bumps `CurrentSchemaVersion` to 63.

Rollback: `bump-version.ps1` without `-Force` refuses any downgrade
that would drop a column required by live code; v63 → v62 succeeds
because the column has no inbound FK.
