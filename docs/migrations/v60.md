# v60 — Event Records + FK rename to `person_record_id` (issue #320)

The v60 schema migration introduces the **Event Record** Person Record
subtype and renames person-scoped FK columns from `soldier_id` to
`person_record_id` to reflect that the FK now references any Person
Record subtype (Soldier, Spouse, Event), not just soldiers.

## Headline changes

- **New `event_person_links` junction table** — many-to-many link
  between Event Record rows (`soldiers.entry_type = 'event'`) and
  any Person Record row. The triple `sync_id` column mirrors
  `records.person_sync_id` for distributed-merge support so two
  nodes sharing Event Records can dedupe on `(event_sync_id,
  person_sync_id)` when the row IDs differ.
- **Four new columns on `soldiers`** for the Event Record subtype:
  `kind TEXT` (free-text, no enum), `begin_date TEXT`,
  `end_date TEXT` (MM/DD/YYYY canonical-date form), and
  `description TEXT` (long-form write-up; mirrors `biography` for
  Person Records).
- **Eight `RENAME COLUMN` statements** across six tables:
  - `records.soldier_id` → `person_record_id`
  - `images.soldier_id` → `person_record_id`
  - `scratchpad_cache.soldier_id` → `person_record_id`
  - `research_tasks.soldier_id` → `person_record_id`
  - `merge_review_conflicts.{local,left,right}_soldier_id`
    → `{local,left,right}_record_id`
  - `duplicate_audit_findings.{left,right}_soldier_id`
    → `{left,right}_record_id`
  - **The FTS5 virtual table's internal `soldier_id UNINDEXED`
    column** is also renamed to `person_record_id` for consistency.
- **FTS5 trigger DROP+RECREATE** for the three `scratchpad_cache_*`
  triggers and the six `soldiers_fts_*` triggers. SQLite does
  **not** auto-update trigger SQL text on `ALTER TABLE RENAME
  COLUMN`, so the triggers must be dropped and recreated with
  the new column name or the next `INSERT/UPDATE/DELETE` on the
  parent table will throw `no such column: new.<old>`. The
  `ensureSoldierFTS` function is itself an idempotent
  DROP+CREATE+INSERT...SELECT cycle, so re-running it is safe
  and produces the same end state.

## What stays the same

- `spouse_soldier_id` (the self-referential FK on `soldiers` for
  the linked-Soldier / Spouse relationship) is **intentionally
  NOT renamed**. It is a Soldier-to-Soldier relationship, not a
  Person Record FK. Events have no spouse.
- The `pdf_excerpt_override` column (added in v55) is reused as
  the per-row short override: "short version of the row's
  long-form text" — biography for Soldier/Spouse, description
  for Event Record. The Typst render path gains a generic
  `render-long-form-inline(s)` helper that dispatches on
  `entry_type` so the same override mechanism works for both
  Person Records and Event Records.
- Wire-compat for v59 `.ddshare` archives: the Go struct
  `Record.PersonRecordID` and `Image.PersonRecordID` carry
  `json:"soldier_id"` so a v59 `.ddshare` round-trips through a
  v60 binary. The `MergeReviewConflict` struct has no json
  tags, so its field rename (`LocalRecordID`, `LeftRecordID`,
  `RightRecordID`) is wire-invisible.

## Fresh-install vs upgrade path

- **Fresh installs** ship with the new column names in the
  inline `const schema` `CREATE TABLE` statements. The v60
  RENAME COLUMN statements guard themselves via `columnExists`
  (no-op when the new column name is already inline).
- **v59 → v60 upgrades** run the v60 block once. The
  `applyAddColumnLoop` (Block 2) adds the four new columns;
  Block 60's sub-block A creates `event_person_links` +
  indexes; sub-block B renames the eight FK columns;
  sub-block C runs `ensureSoldierFTS` to drop+recreate the
  FTS5 triggers; sub-block D backfills `person_sync_id` on
  `records` and `images` for any rows where the v59
  migration was incomplete.

## Reversibility

The v60 block is **PartiallyReversible** (per
`docs/migrations/reversibility.md` Block 18 catalogue entry).
- `RENAME COLUMN` is reversible (the inverse RENAME brings
  the column back to its old name; data is unchanged).
- `CREATE TABLE event_person_links` is reversible
  (`DROP TABLE event_person_links` + the three indexes).
- The FTS5 trigger `DROP+RECREATE` cycle is reversible
  (re-running the inverse cycle with the original column
  names would require temporarily reverting the renames,
  which is unsafe, so the DOWN path is a no-op for the FTS5
  layer; the triggers reference `person_record_id` regardless).
- `ADD COLUMN` is reversible (`DROP COLUMN` works because
  the four new columns are not FK-constrained).

The DOWN runner handles v60 → v59 (per
`TestApplyDownSchema_PartialReversibleStepDown`); v59 → v58
still refuses because Block 17 (the `evidence_type` rename)
is Irreversible.

## New types + helpers

- `models.EntryTypeEvent = "event"` constant. `AllEntryTypes()`
  and `IsValidEntryType()` updated to accept the new value.
- `(*DB).NextEventID()` mints `EVT-NNNNN` Display IDs
  (independent of the per-user node prefix; the `EVT-`
  namespace is its own counter).
- `db.EventDisplayIDNamespace = "EVT"` constant.

## Existing archives migrate transparently

`event_person_links` starts empty so no backfill is needed;
the four new soldiers columns default to NULL. The 8 RENAME
COLUMN statements are guarded by `columnExists` so the
migration is idempotent on re-apply.

Bumps `CurrentSchemaVersion` to 60. No manual steps.

Rollback: `bump-version.ps1` without `-Force` refuses any
downgrade that would drop a table or index required by live
code; v60 → v59 succeeds because Block 60 is
PartiallyReversible.
