# v65 — `restored_at` column on `soldiers` (issue #423)

The v65 schema migration adds a nullable `restored_at TEXT` column
to the `soldiers` table so every row carries the timestamp of the
most recent SQLite-snapshot restore that carried it over. The
motivating case is the #377 slice-2 follow-up: rows that pre-existed
a `restore_point` operation kept the provenance they had at the
time of their original Create, with no record of the restore event
itself. With `restored_at`, a single query answers "when was this
row carried over the most recent restore point?" without grepping
the git log + cross-referencing timestamps.

## Headline changes

- **One new column on `soldiers`**:
  - `restored_at TEXT` — RFC3339 timestamp string, nullable, no
    DEFAULT. The presence/absence of the value is itself the signal:
    NULL = "never carried over a restore point", non-NULL = "carried
    over at that timestamp".
- **The column is nullable + no DEFAULT** so the migration is a
  no-op on data: pre-v65 rows get NULL (not a synthetic "unknown"
  sentinel) and never-restored rows stay NULL forever. This is
  the opposite of the v64 `created_by_*` columns (NOT NULL DEFAULT
  '' + backfill to "unknown") because the absence of `restored_at`
  is meaningful — it answers a yes/no question, not a provenance
  question.
- **Read paths** gain the column at the end of `soldierSelectColumns`
  + a matching `nullStringDest` entry in `soldierScanDest`. Backward
  compat: every existing caller continues to work unchanged
  (the struct field defaults to `""`; the SQL reads NULL and
  stores `""`; the `json:"-"` tag means the field is hidden from
  static archive output for never-restored rows).
- **Write paths are NOT touched by this slice** — Slice 2 of #423
  wires `restoreSnapshotBackup` (in `internal/archive/backup_service.go`)
  to bulk-UPDATE every pre-existing row's `restored_at` after the
  SQLite file swap lands, with the restore timestamp. Slice 1 only
  lands the schema + struct + read path — the per-handler stamping
  is a single line of SQL (one UPDATE) and benefits from a
  fresh-context review pass per the tracer-bullet rule.

## Update semantics (locked, mirrors #377 Decision 3)

The existing `UPDATE soldiers SET ...` statement in
`soldier_service.go:372` does NOT list `restored_at`. The column
is **frozen at the moment the row enters the table** (more
precisely: at the moment the row is carried over a restore point)
and never rewritten by Update. Proven by
`TestRestoredAtPreservedAcrossUpdate`.

## Fresh-install vs upgrade path

- **Fresh installs** ship with the column in the inline `const
  schema` `CREATE TABLE` statement. The v65 ADD COLUMN statement
  guards itself via `columnExists` (no-op when the new column is
  inline). On fresh installs every row has `restored_at = NULL`
  (the implicit default) and stays NULL until a restore point
  stamps it.
- **v64→v65 upgrades** run the ADD COLUMN + the inline-schema is
  out of sync until the upgrade completes. Pre-v65 rows land
  with `restored_at = NULL`; the migration does not backfill a
  synthetic timestamp because the original create-time
  provenance is recorded in `created_by_*` (the absence of a
  restore stamp is the correct value).

## Wire-compat

`models.Soldier.RestoredAt` carries `json:"-"` (not
`json:"restored_at,omitempty"`) — the field is hidden from
static archive output entirely. Justification: `restored_at`
is transport metadata about a specific machine's restore
history, not part of the row's identity. A row restored on
2026-07-08 on machine A is the same row on machine B (which
never had a restore point); the field's value would be
machine-specific noise on the wire. If a future need
surfaces to share restore history, the proper fix is a
separate `restore_history` table (FK to soldier_id) rather
than a per-row column.

## Reversibility

Reversible. `ALTER TABLE soldiers DROP COLUMN restored_at`
works because `restored_at` is not FK-constrained and has
no inbound references. The DOWN path discards the
`restored_at` values for every row, but those values are
transport metadata (not domain data) so the loss is
acceptable on a DOWN-grade. Catalogued in
`docs/migrations/reversibility.md` as **Reversible**.
