# Cemetery roster export — reference artifacts

Captured 2026-08-11 (commit ea9afca0, branch rc/v1.1) as the canonical
reference for the plain-text roster export format.

## Files

| File | Scope | Records |
| --- | --- | --- |
| `cemetery_export_hewitt_bomar_keller.txt` | First 3 cemeteries (Hewitt, Bomar Point, Keller) only — format-test sample | 30 soldiers (6 widows excluded) |
| `cemetery_export_full.txt` | Entire `soldiers` table where `entry_type IN ('soldier', NULL, 'linked_person')` | 518 known + 53 unknown |

## Why these live in the repo

These are the format reference for issue
[#727](https://github.com/valueforvalue/DixieData/issues/727) —
`feat(export): plain-text roster format`. The agent that implements the
issue should diff the new exporter's output against
`cemetery_export_full.txt` (modulo ordering and any cemetery-name
cleaning changes) to verify the contract before closing the slice.

## Format

```
<Cemetery name>
--------------

  <First> <Middle> <Last>  (b <BIRTH_YEAR> | d. <DEATH_YEAR>) <RANK_OUT> | <UNIT>
  ...

<Next cemetery>
---------------
...
```

- Alpha by last name within each cemetery, alpha by cemetery name overall.
- Em-dash (U+2014) for blank fields.
- Soldiers only — `widow`, `wife` excluded.
- `unit` source column is `soldiers.unit` (e.g.
  `Co. E, 29th TX Cavalry Regiment, C.S.A.`); em-dash when blank.
- "Burial Unknown" tail section buckets rows where `buried_in` matches
  `cemetery (not )?known`, `burial (site )?(details? )?unknown`, etc.

## Cleaning rules

`buried_in` strings often carry Find-a-Grave nav cruft after the real
cemetery name. The cleaner cuts at the first occurrence of any marker:

`"Remove Ads"`, `"Memorials Cemeteries Contribute"`, `"function setCookie"`,
`"Copyright ©"`, `"var currentLocal"`, `"window.location.href"`, `"Site Map"`,
`"Privacy Statement"`, `"Terms and Conditions"`.

This split produces the dual "Keller Cemetery" / "Keller Cemetery, Carter
County, Oklahoma, USA" sections in `cemetery_export_full.txt` — two rows
were stored with cruft, three were stored clean. Mutating the DB to merge
them is a separate concern deferred per the user (2026-08-11: "we will
fix that later").

## How these were produced

The 2026-08-11 export was generated by a one-off Python script in the
shell, not committed (REPL discipline per `docs/agents/repl.md`). The
script:

1. Pulled `first_name, middle_name, last_name, rank_out, unit,
   birth_info, birth_date, death_year, buried_in` from `soldiers`.
2. Applied the cleaning rules above.
3. Extracted birth year with the priority chain documented in #727
   (birth_date MM/DD/YYYY → birth_info regex).
4. Sorted and grouped, wrote to disk.

The implementing agent for #727 should re-derive from the same source
table with the same rules; the bytes in this directory are the contract,
not the script.
